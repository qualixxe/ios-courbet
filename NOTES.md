# ios-courbet — engineering log

Port of ios-sweet (iOS 16 XNU + iPhone X userland) from Redmi Note 10 Pro (`sweet`)
to Xiaomi Mi 11 Lite 4G (`courbet`). Upstream: https://github.com/dipa-studio/ios-sweet
(read-only clone `ios-sweet-upstream`, HEAD `45263be`). The old ios-sweet log is

## Handoff (2026-10-29) — patch 0085 was wrong; the full boot console is now readable; exec diagnostics in CI

**The 10-28 "root cause" is retracted — it was a misreading and it was never tested.**

- **Never tested**: every run on 2026-10-29 booted `%TEMP%\kernel.development.sweet`
  dated Oct 27, i.e. built *before* `630f6d8`. The `xnu-kernel-artifact` branch
  (commit `6a28c97`) had not been fetched over it. So no observation can support
  patch 0085 either way.
- **Wrong on the code**: the `Data Abort ... FAR=0x4000` trace in `qemu.log` ends
  with `Exception return from AArch64 EL1 to EL1 PC 0xfffffe0007491aac` — a
  *handled* demand-page fault on the scratch page, not a failed copy. Reading
  `copy_validate()` (osfmk/arm64/copyio.c:131) properly: an address outside
  `current_thread()->map` gives **EFAULT**, a kernel-to-kernel copy gives
  **EXDEV**, and **EINVAL** only comes from a tagged address
  (`user_addr & TBI_MASK`) or an unaligned atomic copy. Allocating the scratch
  page in `kernel_map` therefore cannot fix errno 22 — it moves `copyout(path,
  argv0)` from "user page, faults in on demand" to "kernel VA inside a user
  map", i.e. a *new* failure. Patch 0085 deleted.
- **Static finding worth keeping**: `load_return_to_errno()` (kern_exec.c:6957)
  never returns EINVAL, so the 22 is *not* a `load_return_t` from the Mach-O
  loader. In the non-spawn exec path the only explicit `EINVAL` assignments are
  `task_set_dyld_info` (1782), the `ip_strspace` alignment check in
  `exec_copyout_strings` (5433) and `thread_process_signature` in
  `process_signature` (7547, provably benign: `machine_thread_process_signature`
  always returns KERN_SUCCESS on arm64). Everything else that returns 22 is a
  posix_spawn-only site.

**The whole boot console log is now recoverable (this was the real blind spot).**

`tools/qemu-sweet.py` dumps the 4 MiB kernel console ring that `0047` writes
(`sweet_log_ring` + `sweet_log_total`, captured unconditionally in `_cnputs`)
straight out of guest RAM: one QMP `pmemsave` of the ring's physical range,
`console_text()` unwraps the circular buffer, result → `OUTDIR/console.txt`.
Symbols come from the same Mach-O scan used for `_iso_font`, so no toolchain is
needed. `qmp()` now takes a list of `pmemsave` requests (native QMP, because
HMP's parser mangles paths with `-`). Verified: the 6 GB run produced a
complete, ordered 6.6 kB log ending in the panic; the 256 MB run 11 kB.
The framebuffer only ever shows the last ~75 lines — `research/qemu-poll.py`
(scrape-and-stitch) is superseded by this.

What the full log proves (run `research/qfull2`, Oct-27 kernel, 6 GB root):
mount succeeds (`hfs: mounted iOSRoot`, journal init, `VM Swap Subsystem is ON`)
and **both** init candidates fail identically:

```
load_init_program: attempting to load /usr/appleinternal/sbin/launchd.development
load_init_program: failed loading /usr/appleinternal/sbin/launchd.development: errno 22
load_init_program: attempting to load /sbin/launchd
load_init_program: failed loading /sbin/launchd: errno 22
panic(cpu 0 caller 0xfffffe00077ed450): Process 1 exec of /sbin/launchd failed, errno 22 @kern_exec.c:6929
```

Nothing else prints between the mount and the panic: no AMFI/dyld/HFS error, no
`exec ...` line from `0042`, so the failure is inside `execve()` before any of
the iOS-platform policy branches.

**New patch: `xnu/patches/0085-sweet-exec-diagnostic-log.patch`** — 18 `printf`
checkpoints along exactly that path, so one boot pins the return site:
the map identity of the scratch page (`argmap`/`cur_map`/`thread_map`/`scratch`),
each `copyout` in `load_init_program_at_path`, `namei`, `exec_check_permissions`
(+ `va_mode`), the first-page `vn_rdwr` (+ `resid`), the Mach-O header we read,
`exec_extract_strings`, `load_machfile` (+ `load_return_to_errno`), `activate_exec_state`,
`exec_add_apple_strings`, `exec_copyout_strings`, `task_set_dyld_info`, both
exits of `exec_mach_imgact` (`bad:` / `badtoolate:` + exit-reason code),
`exec_activate_image`'s `bad:` and `__mac_execve`'s exit. Generated by
`mkexecdiag.py` against the post-0001..0084 tree (kept in `%TEMP%`, re-run with
`--base` only if the base changes); `patch -p1 --dry-run` clean, gates green:
`fix_hunks.py` ×2 → 85 files, 0 corrections; `verify_patches.py` → 668 lines,
chain OK.

**Next**: wait for `xnu.yml`, then `git fetch origin xnu-kernel-artifact` and
install that kernel over `%TEMP%\kernel.development.sweet` (the Artifacts API

**What happened since the section below**

- `tools/qemu-sweet.py` no longer needs `llvm-nm`: `--kernel` now decodes the
  framebuffer with a built-in Mach-O symbol scan (`macho_defined_syms`, same
  `LC_SYMTAB` walk `symsweet.py` uses). Combined with `--fail-on-panic` the
  harness is **fail-safe**: exit 0 = no panic visible, 2 = panic decoded into
  `fb.txt`, 3 = undecodable/blank. Verified on the green 64 MB run:
  `{"status": "no_panic_observed", "unknown_glyphs": 0}` rc=0, and the same
  run still reaches `*** SWEET userspace: init running as PID 1 ***`.

  build()` and `qemu-sweet.py` read/copy the ramdisk in 8 MiB chunks and never
  hold it in RAM (before: ~12 GB peak for a 6 GB image; the host has 16 GB).
  Byte-exactness proven: the rebuilt 64 MB payload is SHA-identical to the one

  single-commit branch `qemu-fullroot-log`.

  `dyld_shared_cache_arm64.symbols` → fixed by the `.symbols` exclusion
  (guess: after it, ~5.5 GB content fits the 6 GB volume; the run logs `du`).
- `research/qemu-fullroot.bat`: one command — builds the 8 GB-highmem QEMU ADT
  + payload and boots with `--fail-on-panic --kernel`; kills orphan QEMU first.
- QEMU RAM sizing: `mkadt.py --qemu --highmem --mem 8` → payload
  `mem_size = 0x17cc00000` → `qemu-sweet.py` picks `-m 8G` (virt RAM top
  0x240000000 > payload top ~0x2314d0000 ✓; the tail of the 6 GB ramdisk
  beyond the kernel's declared RAM end 0x22cc00000 is memory the kernel never
  manages — the ADT `RAMDisk` memory-map entry reserves the in-RAM part).

- **launchd exec EINVAL — ROOT CAUSE FOUND AND PATCHED** (commit `630f6d8`):
  **(RETRACTED 2026-10-29 — see the handoff above: the abort was a handled page
  fault, `kernel_map` cannot remove an EINVAL, and the patch was never booted.)**
  With the 6 GB root, QEMU boots the kernel, mounts the HFS+ root, and reaches
  `exec /sbin/launchd` — but panics with `errno 22 (EINVAL) @ kern_exec.c:6929`.
  Investigation (`qemu.log`, `fb.txt`, `symsweet.py`):
  * Data Abort at `__bcopyout+0x1c`, FAR=0x4000 — `scratch_addr` from
    `mach_vm_allocate_kernel()` is 0x4000 (near-NULL page), invalid for `copyout`.
  * Root cause: `load_init_program()` in `bsd/kern/kern_exec.c:6878` calls
    `mach_vm_allocate_kernel(current_map(), ...)`. `current_map()` returns the
    **init process's user map** (bsd_init runs as pid 1 user process, not a
    kernel thread), so the scratch page is allocated in user space at 0x4000
    instead of kernel space. `copyout(path, 0x4000, ...)` faults → every exec
    attempt fails → panic EINVAL.
  * Fix: `xnu/patches/0085-sweet-fix-load-init-program-kernel-map.patch` —
    change `current_map()` to `kernel_map` so `mach_vm_allocate_kernel` allocates
    from the kernel map. Patch pushed as commit `630f6d8`; CI build in flight.

**Status**: CI building kernel with patch 0085. When done, download new kernel
(`%TEMP%\kernel.development.sweet`), `research\qemu-fullroot.bat 240`, read
`fb.txt` — goal is real launchd starting on the courbet kernel in QEMU.
